# U18 Phase 6 — UI (First-Login Guardian Flow + Per-Action OTP)

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development for Task 1; Tasks 2–3 are visual components — pair with superpowers:frontend-design + a browser-QA loop (the `browse`/`gstack` skill) for verification, not just unit tests.

**Goal:** The ward-facing UI for the U18 flow: at first login a minor captures DOB → guardian details (with same-contact warn) → guardian OTP; and every action (apply/connect/accept) shows a "guardian confirmation via OTP" popup that runs the challenge/response before the action completes.

**Architecture:** New API-client methods (`apps/ui/src/lib/consent-api.ts` + `action-api.ts`) call the Phase 4/5 endpoints. A first-login orchestration (extend `use-consent-gate` / the onboarding flow) detects minor status (after DOB) and the ward's profile domain (from their existing bulk-created profile item) to decide whether to run the guardian flow. `action-modal` gains a guardian-OTP step: on a `GUARDIAN_OTP_REQUIRED` per-item error (perform) or 428 mapping, show the OTP popup and resubmit with `guardian_otp`.

**Tech Stack:** React 19 + Vite, TanStack Query, RJSF, the existing `apiClient` (`@/lib/api-client`).

## Global Constraints

- Domain is DERIVED from the ward's existing profile item (bulk-onboarded), not a registration dropdown (dropdown = self-signup fallback only).
- Same-contact: highlight + "you're okay with this?" confirm → sets `sameContactAcknowledged`.
- Per-action: popup "This requires your guardian's confirmation via OTP" → Yes → OTP sent to guardian → enter OTP → action proceeds. Every action (no blanket).
- Reuse existing consent modal/checkbox styling; no new design system.

### Task 2: First-login guardian flow (components — browser-QA)

**Files:**
- Create: `apps/ui/src/components/consent/u18/dob-step.tsx`, `guardian-form-step.tsx`, `guardian-otp-step.tsx`, and an orchestrator `u18-guardian-flow.tsx`.
- Modify: the onboarding/first-login entry (where `useConsentGate` / the consent modal is shown after login) to branch into the U18 flow when the ward is a minor on a `guardian_consent_required` domain.
- Test: component tests (Vitest + Testing Library) for each step's validation + the same-contact highlight; **browser-QA** the full flow.

**Flow:**
1. **DOB step** — month + year pickers (no day). Submit → `submitU18Dob`. If `isMinor === false` → exit to the normal adult consent flow.
2. **Guardian form step** — name, contact, contact-type (phone/email), guardian-declaration checkbox (required). On blur/submit, if the contact equals the ward's own email/phone → **highlight the field** + inline "This is the same as your own contact — are you okay with that?" checkbox; set `sameContactAcknowledged`. Submit → `submitGuardian`; a `409 SAME_CONTACT_NEEDS_ACK` re-opens the highlight if the ack was missing.
3. **Guardian OTP step** — "We sent a code to your guardian." 6-digit input → `verifyGuardian`. On success, continue (guardian terms/privacy recorded server-side). Handle `429`/`503` with friendly copy + resend (re-call `submitGuardian`).

**Domain source:** read the ward's profile item(s) (existing fetch of "my items") → take the domain of their profile; pass it where the flow needs `guardian_consent_required` framing. (No dropdown; self-signup with no profile is a documented fallback.)

- [ ] Build the three steps + orchestrator; wire into first-login; component tests for validation + same-contact highlight; browser-QA the happy path + the same-contact + wrong-OTP paths. Commit.

### Task 3: Per-action guardian OTP popup (action-modal — browser-QA)

**Files:**
- Modify: `apps/ui/src/components/actions/action-modal.tsx` (+ any action trigger that calls `performAction`, e.g. `home-page.tsx`).
- Create: `apps/ui/src/components/actions/guardian-otp-dialog.tsx`.
- Test: component test for the challenge→verify branch; browser-QA apply + connect + accept.

**Flow (challenge/response):**
1. Ward taps Apply/Connect (or Accept). Modal confirms as today.
2. On submit, call `performAction`/`updateActionStatus` **without** `guardianOtp`.
3. If the result is `GUARDIAN_OTP_REQUIRED` (per-item for perform; the same error surfaced for accept), open `guardian-otp-dialog`: **"This requires your guardian's confirmation via OTP"** — the OTP was already sent server-side on that first call. Show a 6-digit input.
4. Ward enters the guardian's OTP → resubmit the SAME action with `guardianOtp` set → success → close, refresh.
5. Map `GUARDIAN_OTP_INVALID` → inline error + retry; `GUARDIAN_OTP_THROTTLED`/`_RATE_LIMITED` → friendly wait copy; `OTP_PROVIDER_UNAVAILABLE` → "guardian confirmation isn't available on this instance."

- [ ] Build the dialog + wire the two-step submit into the action path; component test the branch; browser-QA. Commit.
