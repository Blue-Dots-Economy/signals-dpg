# Notification copy

Signals renders no notification copy. Every email, SMS and WhatsApp message the
API triggers is one **event** posted to notification-service (NS) at
`POST /v1/notify`, carrying an `event_type`, the recipient's network `domain`,
the contact point and plain-text `variables`. NS owns everything a recipient
sees: subjects, bodies, HTML layout, button labels, brand colours, the sender
identity and the channel choice.

## Where copy is edited

Copy is edited in **notification-service, through its admin API**:

- `/v1/admin/templates` — the email, SMS and WhatsApp templates (create, edit,
  preview, publish, retire).
- `/v1/admin/policies` — the policy for each (domain, event) pair, which names
  the templates an event is delivered with.
- `/v1/admin/export` — the live catalogue, for review or for committing back.

A change published there reaches every NS pod within its resolve cache TTL
(`NS_RESOLVE_CACHE_TTL_MS`, default 60 s); the pod that served the admin call
uses it on the next send. Signals needs no redeploy, and no Signals config
changes.

## Where the starting catalogue comes from

Each bluedots-schemas directory that holds a `network.json` also holds an
`ns-catalogue.json`: that network's (or brand's) templates and policies. NS
seeds from it at deploy time (`NS_SEED_FILE`).

The catalogues are generated by hand with this repo's `tools/ns-catalogue/`:

```bash
pnpm --filter ns-catalogue generate <path-to-bluedots-schemas> [--version <v>]
```

It writes `ns-catalogue.json` next to each `network.json`, merging per key the
bundled defaults, then the network's `messages.properties`, then the brand's.
Commit the output to bluedots-schemas. The generator's own inputs under
`tools/ns-catalogue/src/legacy/` are a frozen snapshot of the copy Signals
rendered before the cutover; the golden test checks the generated templates
render byte for byte the same.

Regenerate when a network adds a domain or an action type: NS answers
`422 no_policy` for an event with no policy, and Signals logs it as
`ns_rejected`. A policy can also be added directly through the admin API.

## Signals configuration

Signals needs two things to send notifications:

- **`NOTIFICATION_SERVICE_ENDPOINT`** — the NS base URL.
- **The Keycloak service client** — `KEYCLOAK_API_CLIENT_ID` (default
  `signals-api`) and `KEYCLOAK_API_CLIENT_SECRET`, with `KEYCLOAK_REALM` and the
  Keycloak base URL (`KEYCLOAK_INTERNAL_BASE_URL`, else `KEYCLOAK_BASE_URL`).
  Signals fetches a `client_credentials` token from the realm's token endpoint
  and sends it as `Authorization: Bearer <token>`. The token is cached until
  30 s before it expires and refreshed once on a `401`.

When the endpoint or the client secret is unset, best-effort notifications are
skipped. Support submissions answer `503 SUPPORT_NOT_CONFIGURED`, and guardian
OTP is unavailable as described in `docs/operations/guardian-otp-templates.md`.

These Signals settings feed event variables:

- **`INSTANCE_NAME`** — the "Team \<name\>" sign-off (`teamName`) in action,
  retire, item-lifecycle, support and welcome emails and in the guardian OTP
  emails whose template uses it (see
  `docs/operations/guardian-otp-templates.md`), and the app name in welcome. Set it to the operating org, for example `EkStep` on Blue
  Dot or `ALIMCO` on Purple Dot.
- **`FRONTEND_BASE_URL` / `UI_HOST_BINDINGS`** — the login link (`ctaUrl`) each
  recipient gets, resolved to their own portal.
- **`SUPPORT_EMAIL` / `SUPPORT_CC_EMAIL`** — the support-request recipients.

## NS configuration that recipients see

- **Sender identity** — NS `EMAIL_FROM_NAME` and `EMAIL_FROM_ADDRESS` set the
  visible From on every email. Support requests set Reply-To to the submitter.
- **SMS OTP template** — guardian OTP policies name the SMS `login_otp`
  template, which NS seeds from its vendor settings
  (`SMS_LOGIN_OTP_TEMPLATE_ID` for msg91; `PINNACLE_LOGIN_OTP_TEMPLATE_ID` with
  `SMS_LOGIN_OTP_BODY` for pinnacle). NS publishes a seeded policy only when
  every template it names is active, and seeds each catalogue entry once, so
  configure `login_otp` **before the first NS boot that loads `NS_SEED_FILE`**.
  On a cluster where it was configured later, the guardian OTP policies are
  drafts: publish them through `/v1/admin/policies`
  (`POST /v1/admin/policies/:id/publish`). This applies to every cluster that
  sends guardian OTP, by email or SMS, since each guardian policy carries both
  channels.
