# Secrets

Three environments, three sources. The same set of keys is consumed per service
in each.

## Local development

- Plaintext `.env` at the repo root. It is loaded by
  `scripts/turbo-with-root-env.mjs` and surfaced to each workspace's process
  via Turbo, so every `pnpm dev:*` / `pnpm build` / `pnpm test` script that
  runs through root-level Turbo sees the same env.
- `.env` is gitignored (see `.gitignore`); `.env.example` is the canonical
  template. **Never put real values in `.env.example`.** If you change
  `.env.example`, change the corresponding `process.env.X` default in code so
  a fresh clone without `.env` still boots (see "Anti-patterns" below).
- `apps/api/drizzle.config.ts` does **not** go through Turbo — it reads
  `../../.env` directly via `dotenv.config({ path: '../../.env' })` so
  `pnpm db:push:api`, `pnpm db:generate:api`, and `pnpm db:studio:api` work
  without relying on the root env loader.
- The `apps/api/scripts/db_init.ts` helper (`pnpm db:init:api`) uses the same
  pattern.
- All env vars consumed by the API are validated at boot by Zod schemas in
  `packages/config/src/secrets.ts`. A missing required key crashes the
  process with a readable error before any request is served.

## Kubernetes — default values (`helmcharts/dpg/values.yaml`)

- The umbrella chart renders three Kubernetes Secrets from
  `templates/secrets.yaml`:
  - `dpg-postgres` — Postgres admin/user password (consumed by the bitnami
    Postgres subchart via `existingSecret`).
  - `dpg-redis` — Redis password (consumed by the bitnami Redis subchart).
  - `dpg-api-secrets` — `AUTH_SECRET`, `POSTGRES_USER`, `POSTGRES_DB`,
    `POSTGRES_PASSWORD`, `REDIS_PASSWORD` (consumed by the API pod via
    `envFrom: secretRef:`).
- Values are read from the `credentials.*` block at the top of
  `values.yaml`. The shipped file holds empty placeholders
  (`PG_PW`, `REDIS_PW`, `AUTH_SECRET` markers).
- `helmcharts/dpg/install.sh` fills those placeholders before `helm install`
  via its `generate_passwords()` helper, which writes:
  - `PG_PW = openssl rand -hex 16`
  - `REDIS_PW = openssl rand -hex 16`
  - `AUTH_SECRET = openssl rand -hex 32`
  An inverse helper resets the file back to placeholders before the
  next install run.
- `templates/secrets.yaml` skips emitting a Secret if its password is empty,
  so `helm template` / `helm lint` stay clean before `install.sh` runs.
- Notification-service and match-score (dpg-scoring) secrets follow the
  same pattern — both have a `credentials.<chart>` block in `values.yaml`,
  and the `keyId` / `secret` values must match the corresponding
  `internal-secrets.json` / `auth.keys.json` files mounted into those pods.

## Kubernetes — AWS overlay (`helmcharts/dpg/values-aws.yaml`)

- **No External Secrets Operator, no AWS Secrets Manager wiring today.**
  `values-aws.yaml` only overlays ingress (ALB), persistence (EBS), and
  resource requests/limits on top of `values.yaml`. Secret material still
  comes from the same `credentials.*` block and is still rendered by
  `templates/secrets.yaml` at install time. The operator running
  `install.sh` is responsible for keeping the populated `values.yaml` out
  of git.
- If you need cloud-managed secrets here later (External Secrets Operator
  with `SecretStore` + `ExternalSecret`, AWS Secrets Manager, IRSA on the
  service account), it is **not** wired up today — that is a separate
  workstream and would require new templates plus an ESO install on the
  target cluster (cluster-wide, owned by the platform team, not by this
  repo).
- For ALB the chart expects an ACM certificate ARN; it is supplied at
  install time via
  `--set 'ui.ingress.annotations.alb\.ingress\.kubernetes\.io/certificate-arn=...'`
  rather than via a Kubernetes Secret.

## Required keys

Source of truth: `packages/config/src/secrets.ts`. Each table row maps to a
field on one of the Zod schemas in that file. Update this document whenever
a schema there gains or loses a field.

|---|---|---|

|---|---|---|

Reserved for the Plan 3 derived-signals worker. No Zod schema exists in this

| Key | Required | Notes |
|---|---|---|
| `POSTGRES_URL` | yes | Same connection string as `api`; processor will upsert into derived-signal tables. |

### `ui` (apps/ui)

The UI is a Vite-built static bundle. "Secrets" here are baked at **build
time** into the JS bundle, not read at container runtime. Defaults are read
in `apps/ui/src/lib/api-config.ts`.

| Key | Required | Notes |
|---|---|---|
| `VITE_API_URL` | optional | Defaults to `http://localhost:2742`. Used when the UI talks directly to an API (no nginx proxy). |
| `VITE_API_URLS` | optional | JSON-encoded `{ key: url }` map; adds extra endpoints to the instance selector. Invalid JSON is silently ignored. |
| `VITE_DEFAULT_API_URL` | optional | Wins over `VITE_API_URL` when set. |
| `VITE_SHOW_INSTANCE_SELECTOR` | optional | When `true`, surfaces the instance selector even outside `import.meta.env.DEV`. |
| `VITE_NETWORK_ID` | optional | Comma-separated list of network IDs to scope the UI to. Parsed by `parseNetworkIds` (split on `,`, trimmed, empties dropped) in `apps/ui/src/pages/home-page.tsx` and `profile-form-page.tsx`. Empty/unset = no network filter applied. |

In the default Helm install the UI's nginx reverse-proxies `/api/*` to
`dpg-api:2742`, so `VITE_API_URL` is intentionally left empty in
`values.yaml` (the browser talks to `/api/...` on the UI host).

## Rotation

- `AUTH_SECRET`: rotate by deploying a new value; existing sessions are
  invalidated. There is no backward-compatibility window today — this is a
  known sharp edge.
- `POSTGRES_*` / `REDIS_*`: connection-string rotation is the operator's
  responsibility. Update the relevant Secret (or `values.yaml` +
  `helm upgrade`), then trigger a rolling restart of the api pod (and the
  signal-processor pod once Plan 3 ships).
- `NOTIFICATION_SERVICE_SECRET` / `DPG_SCORING_SECRET`: rotate the
  corresponding key entry in `internal-secrets.json` /
  `auth.keys.json` **and** the matching env var on the api pod in the same
  deploy, otherwise HMAC verification will fail on one side.

## Anti-patterns we've already hit

- **`.env.example` carrying broken defaults.** PRs #4–#6 chased values that
  worked for the original vendor but not for us. When you change
  `.env.example`, also change the relevant `process.env.X` default in code
  so a fresh clone without `.env` still boots (e.g.
  `NETWORK_CONFIG_LOCAL_FILE`'s default in
  `packages/config/src/secrets.ts`).
- **Override-without-merge env vars.** `ALLOWED_ORIGINS` originally
  replaced its defaults instead of augmenting them in dev, which silently
  broke `pnpm dev:ui` after a misconfigured `.env`. New pattern: env vars
  that **augment** defaults in dev and **override** in production. Apply
  the same shape to any future origin-list-style config.
- **Secrets in `values.yaml` once `install.sh` has run.** `install.sh`
  populates `credentials.*` in place; do not commit that file after
  running it. The inverse helper in `install.sh` resets the placeholders
  before the next run — use it if you need a clean diff.
